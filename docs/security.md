# FINX Platform Security Architecture & Guidelines

## 1. Overview
FINX is a B2B milestone-based fiat escrow platform connecting Buyers, Sellers, and Platform Administrators. Because FINX handles business deal agreements and fiat escrow orchestration, security is foundational at every layer of the architecture.

This document outlines the security controls, authentication mechanisms, token lifecycles, and risk mitigation strategies implemented in the FINX backend.

---

## 2. Authentication Architecture

### 2.1 Dual-Token Authentication System (JWT + Refresh Tokens)
* **Access Tokens**:
  * Signed using HMAC SHA-256 (`HS256`) via JSON Web Token standard (RFC 7519).
  * Stateless and short-lived: default **15 minutes** (`900,000 ms`).
  * Contains claims: `sub` (User UUID), `email`, `role` (`BUYER`, `SELLER`, `ADMIN`), `name`, `iat`, `exp`.
  * Verified on every authenticated request by `JwtAuthenticationFilter`.
* **Refresh Tokens**:
  * Cryptographically random 48-byte URL-safe strings generated by `SecureRandom`.
  * Stored in PostgreSQL in **hashed form** (`SHA-256`) to prevent plaintext token leaks if the database is accessed.
  * Long-lived: default **7 days** (`604,800,000 ms`).
  * Features strict **Token Rotation**:
    * Whenever a refresh token is exchanged at `/api/auth/refresh`, the old refresh token is marked revoked (`revoked_at = NOW()`).
    * A completely new access token and new refresh token are returned to the client.
  * **Token Reuse Detection & Revocation**:
    * If an already revoked refresh token is presented at `/api/auth/refresh`, the system detects potential token theft and immediately revokes **all** active tokens belonging to that user, forcing a re-login.
  * Explicit revocation supported via `POST /api/auth/logout`.

## 3. Password Security & Hashing
* Passwords are never stored in plaintext.
* Hashed using **BCrypt** with work factor (strength) **12**.
* **Password Complexity Requirements**:
  * Minimum 8 characters, maximum 100 characters.
  * Enforced by `@Pattern` regex: at least one lowercase letter, one uppercase letter, one digit, and one special character (`@#$%^&+=!._-`).

---

## 4. Role-Based Access Control (RBAC)
FINX strictly enforces permissions based on user roles:
* **BUYER**: Deal creation, milestone definition, escrow funding approval.
* **SELLER**: Deal acceptance, work milestone submission, disbursement receipt.
* **ADMIN**: Platform monitoring, escrow dispute resolution, transaction auditing.

### Privilege Separation:
* **Public Registration Restrictions**:
  * The public `/api/auth/register` endpoint only permits `BUYER` and `SELLER` registration.
  * Any request attempting to register with `ADMIN` role is rejected with `400 Bad Request` ("ADMIN accounts cannot be registered publicly").
  * Administrator accounts must be provisioned through secure infrastructure seed pipelines or direct database scripts.

---

## 5. Rate Limiting & Brute-Force Protection
* Implemented via `AuthRateLimitFilter` targeting `/api/auth/**`.
* Limits requests per client IP (default: **60 requests per minute**).
* Uses atomic counters windowing requests by client IP (supporting `X-Forwarded-For` proxy headers).
* Exceeding the limit responds immediately with `429 Too Many Requests`.

---

## 6. Injection Defense & Data Sanitization
* **SQL Injection Protection**:
  * All database interactions are managed via Spring Data JPA and Hibernate.
  * All dynamic queries use parameterized queries and object-relational mappings. Raw string concatenation in queries is strictly prohibited.
* **Flyway Migrations**:
  * Schema creation is versioned and validated via Flyway (`V1__create_users_and_auth_tables.sql`).
  * `ddl-auto` is set to `validate` in dev and `none` in production to prevent runtime schema tampering.

---

## 7. Cross-Origin Resource Sharing (CORS)
* Enforced via Spring Security `CorsConfigurationSource`.
* Configurable allowed origins via `CORS_ALLOWED_ORIGINS` environment variable (defaults to `http://localhost:3000`).
* Permitted methods: `GET`, `POST`, `PUT`, `DELETE`, `PATCH`, `OPTIONS`.
* Credential support enabled (`allowCredentials: true`) for secure cookie/header exchange.
* Pre-flight caching configured with `maxAge: 3600` seconds.

---

## 8. Audit Logging & Compliance
* All critical security actions are captured in the immutable `audit_logs` table:
  * `USER_REGISTERED`
  * `USER_LOGIN`
  * `FAILED_LOGIN_ATTEMPT`
  * `TOKEN_REFRESHED`
  * `REVOKED_TOKEN_REUSE_ATTEMPT`
  * `USER_LOGOUT`
* Log entries capture `actor_user_id`, `action`, `entity_type`, `entity_id`, `metadata`, and timestamp.
* Uses isolated transactions (`REQUIRES_NEW`) to guarantee audit persistence even if non-critical operations fail.

---

## 9. Secret Management & Production Hardening
* **No Hardcoded Secrets**: Secrets such as `JWT_SECRET`, database passwords, and Redis credentials are externalized via environment variables.
* **Logging Hygiene**:
  * Passwords, plaintext tokens, and sensitive personal information are never logged.
  * Global exception handling sanitizes stack traces and returns standardized `ErrorResponse` payloads.
* **Container Security**:
  * Docker container runs as a non-root, unprivileged user (`finxuser:finxgroup`).
  * Minimal Alpine JRE runtime reduces attack surface.
